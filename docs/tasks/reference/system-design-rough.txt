2. DDIA — The Whole Book in Interview Terms
Chapter 1 — Reliable, Scalable, Maintainable Applications

This chapter looks simple, but it gives you the vocabulary used throughout system design.

Reliability

A reliable system continues behaving correctly despite failures.

Failures include:

Process crash
Network failure
Disk failure
Machine failure
Dependency failure
Human/configuration failure

Reliability isn't merely:

"The server is up."

It means:

Request
   ↓
Correct result
   ↓
Despite partial failures
Availability

Probability that the system is operational when requested.

Example:

99%      ≈ 3.65 days downtime/year
99.9%    ≈ 8.76 hours/year
99.99%   ≈ 52.6 minutes/year
99.999%  ≈ 5.26 minutes/year

These numbers are extremely useful in interviews.

Scalability

There is no single "scalable architecture."

Instead ask:

What dimension is growing?

Data size
Vertical scaling

16 GB → 128 GB RAM

Simple, but limited.

Horizontal scaling
          Load Balancer
          /     |     \
       Node1  Node2  Node3

Now the problem becomes:

7. Leader-Based Replication
             Writes
               ↓
            Leader
          /        \
         ↓          ↓
     Replica A   Replica B

All writes go to leader.

Reads may go:

Leader
Replica A
Replica B

Problem:

Replication lag
t1: write user.balance = 500

Leader
balance = 500

Replica
balance = 400

Immediately reading from the replica may return stale data.

This creates:

Read-after-write inconsistency

Example:

POST /profile
      ↓
success

GET /profile
      ↓
old profile

Interviewers love this problem.

8. Synchronous vs Asynchronous Replication
Synchronous
Write
 ↓
Leader
 ↓
Replica ACK
 ↓
Client ACK

More durable/consistent.

But latency increases.

Asynchronous
Write
 ↓
Leader
 ↓
Client ACK

Replica replication happens later

Lower latency.

But recent writes can be lost if the leader dies before replication.

So:

Consistency ↑
Latency ↑

Availability/performance ↑
Consistency may ↓

This trade-off is a core distributed-systems skill.

9. Multi-Leader Replication
Region A ───── Region B
   Leader  ←→  Leader

Useful for multi-region writes.

But now:

A writes X
B writes Y

What happens when both modify the same record?

You have conflict resolution.

Possible strategies:

Last write wins
Merge
Application-specific resolution
CRDT-style structures

The key lesson:

Multi-leader systems increase availability and locality at the cost of complexity.

12. Consistent Hashing

Important for system design.

Imagine:

             Node A
              ●

      Node D ●     ● Node B

              ●
           Node C

Keys are mapped onto a hash ring.

When a node disappears:

23. Idempotency 🔴

A request is idempotent when repeating it produces the same final effect.

POST /payment
Idempotency-Key: abc123

Server:

abc123 → already processed

Return existing result instead of executing again.

Typical pattern:

Request
  ↓
Idempotency key
  ↓
Check store
  ↓
already exists?
 ┌──────────────┐
 │ Yes          │ No
 ↓              ↓
return result   execute
                ↓
             store result

This is one of the most important concepts for:

24. Timeouts Are Not Failures You Can Fully Understand

Suppose:

A → B

A waits 3 seconds.

Timeout.

What happened?

Possibilities:

1. B never received request
2. B received it but failed
3. B processed it
4. B processed it but response was lost
5. Network delayed response

Therefore:

A timeout does not necessarily mean the operation failed.

This single idea explains a huge amount of distributed-systems complexity.

27. Chapter 9 — Consistency and Consensus 🔴

This is probably the chapter you should study hardest.

Linearizability

Very roughly:

Once a successful write completes, every subsequent read sees it.

Imagine:

t1       t2        t3
write    read      read
 100      100       100

Strong guarantee.

Useful for things such as:

locks
leader election
unique ownership
critical state

But stronger consistency generally costs more.

28. Sequential Consistency

Operations appear in a valid global ordering while preserving each client's order.

Not necessarily the exact real-time ordering required by linearizability.

You should know the distinction conceptually.

29. Eventual Consistency

Example:

Primary
  ↓
Replica A
Replica B
Replica C

Immediately after a write:

A = new
B = old
C = old

Eventually:

A = new
B = new
C = new

This is common when availability and latency are prioritized over immediate consistency.

30. CAP Theorem

This gets badly memorized in interviews.

CAP says that under a network partition, a distributed system must choose between:

Consistency
Availability

because partition tolerance is not realistically optional in a distributed system.

Think:

             Network Partition
                   ↓
          ┌────────┴────────┐
          ↓                 ↓
      Consistency       Availability

Not:

"You can only have two of three."

That explanation is too simplistic.

The important condition is:

During a partition, you cannot simultaneously guarantee both strong consistency and availability.

31. PACELC

Useful interview bonus.

CAP addresses partitions.

PACELC asks:

P → A or C
Else
L or C

Meaning:

If Partition:
    Availability vs Consistency

Else:
    Latency vs Consistency

This is closer to how real systems are designed.

32. Consensus

Do not confuse:

Replication
Quorum
Leader election
Consensus

Consensus is about multiple nodes agreeing on a value/state despite failures.

Examples:

Raft
Paxos

A simplified Raft mental model:

             Leader
            /      \
       Follower   Follower

Leader coordinates replicated state.

If leader dies:

Election
   ↓
New leader
   ↓
replication continues

You don't need to implement Raft in a normal interview.

You do need to understand why consensus exists.

33. Quorum

W + R > N

the read/write sets overlap.

This can provide stronger consistency depending on the system's implementation.

Know:

R
W

and what changing them does to:

38. Delivery Semantics

This is critical for event-driven interviews.

At-most-once
process 0 or 1 times

Possible message loss.

At-least-once
message will eventually be delivered
but may be delivered multiple times

Therefore:

consumer must be idempotent
Exactly-once

People often say:

"Kafka gives exactly once."

That's incomplete.

Exactly-once is usually a property of a carefully designed processing pipeline, not magic removal of all duplicate effects.

For business operations:

at-least-once
+

is often the practical approach.

39. Ordering

61. Your First Core Cheat Sheet

Memorize these relationships, not isolated definitions:

Replication
    → availability + read scaling
    → introduces consistency/lag problems

Partitioning
    → storage + write scalability
    → introduces routing/hotspot problems

Async messaging
    → decoupling + buffering
    → introduces eventual consistency

Retries
    → resilience
    → introduce duplicates

At-least-once delivery
    → reliability
    → requires idempotency

Distributed transactions
    → consistency across services
    → introduce coordination complexity

Strong consistency
    → easier reasoning
    → often higher latency/lower availability

Event-driven architecture
    → loose coupling
    → harder debugging/order/consistency

Caching
    → lower latency/load
    → invalidation/staleness problems

Sharding
    → horizontal scale
    → cross-shard query/transaction complexity

This is the actual DDIA mental model you should carry into interviews.
