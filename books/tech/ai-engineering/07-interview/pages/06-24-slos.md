## What SLOs would you set for an LLM service?

- An **SLO (service level objective)** is a measurable promise about behaviour. For LLMs, set them across latency, availability, **and quality** — quality is the unusual one.
- Candidate SLOs:
  - **Latency** — e.g. p95 TTFT < 800 ms, p95 TPOT < 50 ms (define per surface; voice is stricter than batch).
  - **Availability** — successful-response rate (including fallbacks) ≥ 99.9%.
  - **Quality** — e.g. groundedness ≥ X%, task-success ≥ Y%, refusal/hallucination rate ≤ Z% on a monitored sample. Harder to measure, but it's what users actually care about.
  - **Cost** — a soft SLO / budget per request.
- Why quality SLOs matter: a service can be fast and up while giving wrong answers — "green dashboards, bad product." You need a measured quality bar with alerting.
- Then run an **error budget**: if you're burning it (latency or quality), slow risky changes and fix reliability before shipping features.

:::interview
What's really being tested: that LLM SLOs must include a measured **quality** target (not just latency/availability), with percentiles and an error-budget discipline — the thing teams forget.
:::
