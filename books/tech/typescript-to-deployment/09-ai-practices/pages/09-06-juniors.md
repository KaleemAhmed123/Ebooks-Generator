## Junior engineers

- This is the part of adoption most teams handle badly, and the cost is delayed by a year, which is why it goes unnoticed
- **The skill that matters now is judging code, and judgement is built by writing code and being wrong.** An engineer who delegates from day one skips the building

### The failure mode

- Output looks good immediately, so nobody worries
- They cannot debug, because they never built a model of anything
- They cannot review, because they cannot tell plausible from correct
- **They cannot tell when the agent is wrong**, which is the entire job now

### What actually works

| Practice | Why |
|---|---|
| **use it to explain, not to write** | the best possible tool for reading unfamiliar code |
| **write it first, then compare** | the comparison is the lesson |
| **debug by hand, always** | this is where the mental model comes from |
| **review real pull requests early** | judgement is the skill, so practice it |
| **explain every merged change out loud** | the same test as Module 5, applied as teaching |

### What to say plainly

- **"Use it to understand. Write the important parts yourself for now."** That is the whole guidance, and it is not condescension
- **A senior engineer delegating implementation is spending a model they already have.** A junior doing the same is skipping the acquisition

### The team's part

- **Do not measure juniors on output.** It removes the reason to do anything the slow way
- **Pair on review.** Watching someone find a subtle bug in a plausible diff teaches more than any explanation
- **This is not a reason to stop hiring juniors.** It is a reason to change what the first year looks like
