## Infrastructure as code

- Everything in this booklet has been shown as CLI commands, because that is how you learn what the pieces are
- **Running those commands by hand in production is how an environment becomes unreproducible.** Nobody remembers what was clicked, and staging drifts from production in ways nobody can list
- **Infrastructure as code makes the infrastructure a file in the repository**, reviewed, versioned, and applied by a pipeline

### What it gives you

| Benefit | Because |
|---|---|
| a review | a change is a pull request |
| a second environment | apply the same code with different variables |
| a rebuild | the account can be recreated from the repository |
| a diff before it happens | `plan` shows exactly what will change |
| an audit trail | git history is the change log |

### The three options

| Tool | Written in | Fits |
|---|---|---|
| **Terraform / OpenTofu** | HCL | **the default.** Multi-cloud, huge ecosystem |
| **AWS CDK** | TypeScript | a team that would rather write TypeScript than HCL |
| **CloudFormation** | YAML or JSON | AWS-only, no extra tooling, verbose |

- **SST and the Serverless Framework** sit on top of CDK and CloudFormation for application-shaped deployments

### The rules whichever you pick

- **The state file is critical and shared.** Store it remotely with locking, never on a laptop
- **Never change infrastructure in the console.** A manual change is reverted by the next apply, or worse, silently kept and forgotten
- **`plan` in the pull request, `apply` on merge.** The diff is the review
- **Start with what changes.** Networking, databases and load balancers are worth codifying first; a one-off scratch instance is not
