## The Model Context Protocol

- Every agent framework invented its own way to describe a tool, so the same integration was rewritten for each one
- **MCP is a standard protocol between an agent and a set of tools**, so a tool server is written once and any client can use it
- It plays the role for tools that a database driver plays for databases: one interface, many implementations
- It is JSON-RPC over stdio for a local process, or over HTTP for a remote one

| MCP exposes | Is |
|---|---|
| **tools** | functions the model can call |
| **resources** | data the client can read, like a file or a row |
| **prompts** | reusable prompt templates the user can pick |

### Where it fits in a backend

- **Wrapping an internal service** so several agents can use it without each embedding a client
- **Consuming a third-party server** for a system you did not build, instead of writing tool definitions for its API
- **Local development tools**, which is where most engineers meet it first

### The judgement

- **A single agent calling three of your own functions does not need MCP.** A tool definition is fifteen lines and adds no process
- It earns its place when the same tools serve several agents or clients, or cross a team boundary
- **A remote MCP server is a public API.** It needs authentication, authorization, rate limiting and audit logging, exactly as Booklet 6 describes. It getting called by a model changes none of that
