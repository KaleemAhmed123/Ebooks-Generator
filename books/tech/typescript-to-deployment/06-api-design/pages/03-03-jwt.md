## JSON Web Tokens

- A **JWT** is three base64 segments joined by dots: a header, a payload of claims, and a signature over both
- The signature proves it was issued by someone holding the key and has not been altered since
- Nothing in it is encrypted. The payload is readable by anyone who has the token

```
  header                payload                        signature
```

```json
{ "sub": "u_1", "role": "seller", "iss": "orders-api",
  "aud": "storefront", "exp": 1756512000, "iat": 1756511100, "jti": "t_9f1" }
```

| Claim | Means |
|---|---|
| `sub` | who the token is about |
| `iss` | who issued it |
| `aud` | who it is for |
| `exp` `nbf` `iat` | expires, not before, issued at |
| `jti` | a unique id for this token, used for revocation lists |

### The five mistakes

- **Decoding instead of verifying.** `decode` reads the payload and checks nothing. Anyone can write a payload
- **Not checking `iss` and `aud`.** A token minted for another service verifies perfectly against a shared key
- **Trusting `alg` from the header.** The `none` algorithm and the RS256-to-HS256 confusion attack both live here
- **Putting secrets in the payload.** It is base64, not encryption
- **Putting a permission list in the payload.** Permissions change and the token does not, so a demoted user keeps their old access until it expires
