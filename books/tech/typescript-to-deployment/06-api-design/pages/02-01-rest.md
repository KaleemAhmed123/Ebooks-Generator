# Module 2 - Designing a REST API

## What REST actually is

- Before REST, every API invented its own verbs, its own envelope and its own error format, and every client was written from scratch
- Roy Fielding described REST in 2000 as a set of constraints rather than a format, and the useful ones are few
- **Resources, not actions.** The API exposes nouns, and HTTP methods supply the verbs
- **Uniform interface.** The same method means the same thing on every resource, so a client learns the rules once
- **Stateless.** The server keeps no per-client session between requests
- **Cacheable.** Responses say whether they may be stored and for how long
- Most APIs called REST satisfy the first three and ignore the rest, which is fine and worth being honest about
- The value is not purity. It is that a caller who has used one REST API can guess how yours behaves

### The test that matters

- Can a caller predict the URL and the method for an operation they have not read about
- If yes, the design is doing its job. If every endpoint is a special case, the convention has bought nothing
