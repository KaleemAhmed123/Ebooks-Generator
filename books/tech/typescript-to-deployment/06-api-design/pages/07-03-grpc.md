## gRPC

- Between two services you control, JSON over HTTP is doing work nobody needs
- The field names are transmitted on every message, parsing is string work, and neither side is checking the other kept its promises
- **gRPC** replaces that with a contract file and a binary format
- The contract is a `.proto` file that generates both the server interface and the client, so the two cannot drift
- **Protocol Buffers** encode field numbers rather than names, so payloads are several times smaller and parsing is far cheaper
- It runs on HTTP/2, so it gets multiplexing and real streaming, in either direction or both
- Built at Google and open sourced in 2015, from an internal system they had run for years

```proto
service Orders {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrders (WatchRequest) returns (stream OrderEvent);
}

message Order {
  string id = 1;
  int64 total_paise = 2;
  OrderStatus status = 3;
}
```

- The numbers are the wire format. **Never reuse a number** after removing a field, or old clients misread new data

### Where it fits and where it does not

- **Yes** for internal service-to-service, especially high volume or streaming, and especially across languages
- **No** for a public API. It is not readable in a browser, `curl` cannot exercise it, and every consumer needs generated code
- Browsers cannot speak it directly at all, which is what gRPC-Web and a proxy exist to work around
