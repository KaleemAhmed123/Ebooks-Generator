## MVCC — readers don't block writers

- Naively, safe concurrency needs locks: a writer locks a row, readers wait. That serialises everything and kills throughput. **MVCC** (Multi-Version Concurrency Control) removes the conflict entirely: instead of overwriting a row, a write creates a **new version** of it, and each transaction reads from a **consistent snapshot** of the versions that were committed when it began. **Readers never block writers, and writers never block readers** — they're looking at different versions.

- Mechanically, each row version carries the transaction IDs that bound its life (`xmin` = created by, `xmax` = deleted/superseded by). A transaction's snapshot says which IDs are visible to it, so everyone sees a stable, self-consistent view without locking. This is how Postgres delivers snapshot isolation (Booklet 3) cheaply, and it's why a long report doesn't block live writes.
- The price is **dead tuples**: superseded versions pile up on disk and must be cleaned. Postgres runs **`VACUUM`** (automatically, via **autovacuum**) to reclaim space from versions no transaction can still see.

:::warn
A **long-running transaction** is MVCC's enemy. Because `VACUUM` can only remove versions **older than the oldest still-running transaction's snapshot**, one forgotten transaction left open (an idle-in-transaction connection, a stuck analytics query) **pins every dead version cluster-wide** — tables bloat, disk fills, and queries slow as they wade through dead tuples. In the extreme it risks transaction-ID **wraparound**, which can force the database read-only. Monitor `pg_stat_activity` for long/idle-in-transaction sessions and set `idle_in_transaction_session_timeout`. The cause is almost never "VACUUM is broken" — it's a transaction someone never closed.
:::
