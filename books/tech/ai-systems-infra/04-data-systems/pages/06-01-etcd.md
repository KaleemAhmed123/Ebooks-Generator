# The Coordination Store

## etcd

- Not every datastore is for your application's data. **etcd** is a **coordination store**: a small, distributed, **strongly consistent** key-value store whose job is to hold the *critical* state a cluster must all agree on — configuration, membership, locks, leader election, feature flags. It runs the **Raft** consensus protocol (Booklet 3) directly, so every write is committed by a **quorum** and all members apply it in the same order. It is the CP corner of CAP made into a product: under a partition it **stops accepting writes** on the minority side rather than diverge.
- It's deliberately **not** a general database. It holds **small** data (megabytes, not terabytes), optimises for **consistency and change-notification** over throughput, and keeps everything that matters replicated across an odd number (3 or 5) of members. Two features make it the coordination substrate others build on:
  - **Watches** — a client opens a gRPC stream and is **notified the instant a key changes** (Booklet 2's long-lived server-stream). This is how components react to state changes without polling.
  - **Leases + compare-and-swap** — a key can be tied to a **lease** that expires unless renewed (the basis of liveness/heartbeats), and atomic CAS enables correct **locks and leader election** (with Booklet 3's fencing).
- This is why **Kubernetes keeps its entire cluster state in etcd** (Booklet 6): every object you create is a committed etcd key, every controller **watches** etcd for changes and reconciles toward them, and leader election among control-plane components uses etcd leases. When people say the control plane is "consistent," they mean etcd's Raft log is.

:::note
The contrast that places etcd correctly among this booklet's stores: Postgres/Cassandra/Dynamo optimise for **holding lots of data and serving queries**; etcd optimises for **a little data everyone must agree on, with instant change notification**. Using etcd as an application database (large values, high write volume) will melt it; using a throughput-optimised database for leader election gives you split-brain. Different jobs, different tools — the Module 3 selection framework, extended to coordination.
:::
