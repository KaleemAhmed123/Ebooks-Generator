## Workspaces and multi-environment

- You need **dev, staging, and prod** from one codebase — identical shape, different sizes, separate state (an apply to dev must never touch prod). There are two common structures, and picking the wrong one causes real accidents.
- **Workspaces** — one configuration, multiple **named states** (`terraform workspace new staging`). The *same* code applies to whichever workspace is selected; `terraform.workspace` lets you vary values (`count = terraform.workspace == "prod" ? 3 : 1`). Cheap, but with a sharp edge: the active workspace is **invisible global state in your shell**, so running `apply` thinking you're in `staging` when you're in `prod` is a classic, destructive mistake. Workspaces fit when environments are **nearly identical**.
- **Directory-per-environment** — a folder per env (`envs/prod`, `envs/staging`), each with its **own backend** (its own state `key`) and its own `.tfvars`, all calling the **same shared modules** (Module 2.3). The environment is **explicit in the path you're standing in**, differences live in plain files, and prod has its own backend you can lock down with separate IAM. More files, far less footgun — and the generally recommended pattern for real teams.

- The real design rule: **duplicate the thin env wiring, share the thick logic.** Each env folder is small — a backend block, a `.tfvars`, and a handful of `module` calls. The substance (how a VPC or cluster is built) lives **once** in shared modules. You get per-env isolation *and* DRY, without workspaces' hidden-selection hazard.

:::note
Whichever you pick, **state isolation per environment is non-negotiable** — prod gets its own state object and ideally its own bucket/account, so no plan, lock, or `destroy` can cross from a lower environment into prod. Large orgs go further and separate by **account** (Booklet 5): a dedicated prod AWS account means even a maximally wrong apply lacks the credentials to touch it. Isolation is defence in depth, not just tidiness.
:::
