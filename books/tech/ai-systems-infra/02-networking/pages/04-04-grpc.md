## gRPC

- **gRPC** is a remote-procedure-call framework: you call a method on a remote service as if it were local. It rides **HTTP/2** (for multiplexing and streaming) and encodes messages with **Protocol Buffers** — a binary, schema-defined format. You write a `.proto` contract, generate typed client and server stubs in any language, and the wire format is small and fast.
- Against REST/JSON the trade is clear: gRPC is **binary and typed** (smaller payloads, compile-time-checked contracts, built-in streaming), where JSON is **human-readable and universal** (trivial to curl, debug, and consume from a browser). gRPC wins inside a system between services; JSON/REST wins at the public edge and for humans.
- It offers four call shapes: **unary** (one request, one response), **server-streaming**, **client-streaming**, and **bidirectional streaming** — all multiplexed over the one HTTP/2 connection.

:::note
This is why infrastructure control planes speak gRPC/protobuf. **etcd**'s API is gRPC; the **Kubernetes** API server stores and transmits objects as protobuf internally; service meshes configure their proxies (Envoy's xDS) over gRPC streams. When you later watch a controller "watch" the API for changes (Booklet 6), that's a long-lived gRPC server-stream delivering events. Knowing gRPC is HTTP/2 + protobuf demystifies the whole control-plane layer.
:::

- Operational note: because gRPC pins a long-lived HTTP/2 connection, naive L4 load balancing sends **all** of a client's calls to one backend (it balances connections, not requests). gRPC needs **L7-aware** balancing or client-side load balancing — a concrete reason the next module's L4-vs-L7 distinction matters.
