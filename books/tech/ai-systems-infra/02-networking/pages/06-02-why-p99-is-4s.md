## Why p99 is suddenly 4 seconds

- A slow request is not one number — it's a **sum of phases**, and the fix depends entirely on which phase grew. `curl -w` breaks a single request into exactly those phases, and that breakdown is where every latency investigation starts:

- Read the phase that grew, and the cause narrows to a layer:
  - **DNS** large → stale/slow resolver, `ndots` amplification (Module 3).
  - **Connect** large → cross-AZ/region distance, SYN loss/retransmits, or **connection-pool wait** (the pool is too small — Module 5, and it hides here as "connect" time).
  - **TLS** large → handshake cost on new connections → you aren't reusing connections.
  - **TTFB** large → the server is slow (CPU, GC, a slow query, a lock — Booklet 1's D-state), not the network.
  - **Transfer** large → payload size or bandwidth/MTU.

:::incident
"p99 is 4s, but only across availability zones." Cross-AZ adds ~1 ms RTT per hop — tiny, until your request makes an **N+1 fan-out** of 50 sequential calls, each paying that RTT, each maybe missing the connection pool and re-handshaking: 50 × (connect + TLS + 1 ms) across AZs balloons into seconds, while each individual call looks "fine". The fix isn't the network — it's **batch the calls, reuse pooled connections, or co-locate the chatty services in one AZ**. This is the single most common "the network is slow" ticket that isn't the network.
:::
