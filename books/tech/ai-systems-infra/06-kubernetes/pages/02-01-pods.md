# Running Workloads

## Pods

- A **pod** is the smallest thing Kubernetes runs: **one or more containers that share a network namespace, an IPC namespace, and volumes** (Booklet 1's namespaces, applied as a group). They are co-scheduled — always on the same node — and they share **one IP address**, so containers in a pod talk over `localhost` and see each other's ports.
- The sharing is held together by a hidden **pause container**: it is started first, owns the pod's network and IPC namespaces, and does nothing but stay alive so the namespaces persist even as app containers restart. The app containers *join* the pause container's namespaces. That's the mechanism behind "one IP per pod."

- **Multi-container pods** are for containers that *must* live together: a logging/metrics **sidecar**, a proxy, a file-syncer. The rule of thumb — one main process per container, extra containers only when they share the pod's lifecycle and resources. Unrelated services go in *separate* pods so they scale and fail independently.
- **Pods are cattle, not pets.** A pod is disposable and has no self-healing of its own — if its node dies, the pod is gone. You almost never create a bare pod; you create a **controller** (Deployment, Job, StatefulSet) that creates and *replaces* pods. The pod is the unit of running; the controller is the unit of *keeping it running*.

:::warn
A bare pod (`kubectl run` with no controller) that lands on a node which then reboots or is drained **does not come back** — nothing owns its desired state. The same for a pod whose node fails: its replacement only appears if a Deployment/ReplicaSet is asking for it. "My pod vanished and never returned" is almost always a workload created without a controller.
:::
