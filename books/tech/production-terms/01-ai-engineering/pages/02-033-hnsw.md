## HNSW

*Hierarchical Navigable Small World*

The index most vector databases use by default: a layered graph descended from
coarse to fine. Fast and accurate, with high memory use and awkward deletes.

`efSearch` trades latency for recall at query time. `M` trades memory for
accuracy at build time. Both need tuning against a labelled set, not against the
documentation's default.

### How it works

Picture a road network in layers. The top layer has only motorways connecting
distant cities — few nodes, enormous hops. Below it, A-roads. Below that, local
streets.

To reach an address you start on the motorway, cover most of the distance in a
few jumps, then descend to progressively finer roads for the last stretch.

HNSW does exactly this with vectors, so you reach the right neighbourhood in a
number of steps that grows logarithmically with the dataset rather than
linearly.

### In practice

Two costs matter operationally, and neither appears in a benchmark.

**Memory is high.** The graph edges sit in RAM alongside the vectors, often
roughly doubling the requirement.

**Deletion is awkward.** Removing a node damages the graph's connectivity, so
most implementations tombstone rather than truly delete. A high-churn collection
degrades over time and needs periodic rebuilding — which is a scheduled job
somebody has to own.
