## Deduplication keys

- Absolute state changes aren't always possible (e.g., sending an email). If the operation itself cannot be idempotent, you must build an idempotency layer using **Deduplication Keys**.
- Every event must include a unique `eventId`. Before processing, the consumer checks a fast storage layer (like Redis or a Postgres unique constraint) to see if it has seen this ID recently.

```typescript
import { redis } from './redis';

async function processOrder(event) {
  // setNX = Set if Not eXists
  // We use the unique eventId as the key, and expire it after 7 days
  const isNew = await redis.setnx(`processed:${event.eventId}`, 'done', 'EX', 604800);
  
  if (!isNew) {
    console.log(`Duplicate event ${event.eventId} detected. Skipping.`);
    return; // Safely ignore!
  }

  // Safe to process...
  await sendShippingEmail(event.userId);
}
```

- The lock must expire eventually to prevent Redis from running out of memory. 7 to 14 days is usually enough time for any redelivered messages to flush out of the system.

### The failure

- Using the payload hash as the deduplication key. A team wants to deduplicate events, but the upstream team refuses to add an `eventId` to the schema. The developers decide to create a hash of the JSON payload (e.g., `md5(payload)`) and use that as the key. A user buys a $5 coffee at 9:00 AM. They buy another $5 coffee at 2:00 PM. The JSON payloads are completely identical. The hash is identical. The deduplication layer blocks the second purchase, assuming it's a redelivered duplicate. You must use a unique identifier generated by the *source*, not a hash of the data
