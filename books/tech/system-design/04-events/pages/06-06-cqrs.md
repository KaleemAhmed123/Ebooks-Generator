## CQRS

- If the source of truth is an append-only log of events, how do you power a UI dashboard that says "Show me the top 10 users with the highest balances"? You cannot iterate through 50 million events in real-time.
- You must use **CQRS (Command Query Responsibility Segregation)**. This pattern strictly separates the write path (Command) from the read path (Query).

- The Write Path only appends to the Event Store. Asynchronously, a background worker (a *Projector*) listens to the Event Store and updates a separate database (the Read Model) optimized purely for the UI's needs (e.g., a denormalized Postgres table or a Redis cache).

### The failure

- Reading directly from the event store. Event Sourced databases (like EventStoreDB) are optimized for appending and for querying a single stream by ID. They are terribly slow at complex aggregations or `JOIN` queries. If you try to power a complex UI dashboard directly by querying the Event Store, the page will take 30 seconds to load. You must bite the bullet and build a separate Read Model using CQRS
