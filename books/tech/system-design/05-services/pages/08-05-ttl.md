## TTL (Time To Live)

- The easiest way to keep a cache vaguely consistent with a database is to give every cached item an expiration time, called a TTL (Time To Live). When the TTL expires, the cache deletes the item. The next request will miss, read the fresh data from the database, and insert a new TTL

| Data Type | Acceptable Staleness | Suggested TTL |
|---|---|---|
| **Bank account balance** | None | 0 (Do not cache) |
| **User profile settings** | Seconds | 10s - 60s |
| **Product catalog description** | Hours | 1h - 24h |
| **Historical invoice PDF** | Years | Infinite |

- You should pick a TTL based strictly on the product requirements for staleness. Do not just pick "5 minutes" out of habit

### The failure

- The failure is relying on a TTL as your *only* invalidation strategy for data that changes unpredictably and must be correct
- If a user changes their password, and you cache the password hash with a 1-hour TTL, the user will be able to log in with their *old* password for an hour, and they will be locked out if they try to use their *new* password. If the data must be correct immediately upon writing, you cannot rely solely on a TTL. You must actively invalidate the cache
