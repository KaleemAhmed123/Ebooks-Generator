## TTL

- A **TTL** is the simplest invalidation there is: the entry deletes itself, the next read misses and refills. It requires no coordination with the write path, which is why it is everywhere, and it guarantees exactly one thing — staleness is bounded by the number chosen

| Data | How stale may it be | TTL that follows |
|---|---|---|
| Account balance | not at all | do not cache; read it |
| Permissions and roles | seconds, and revocation must be instant | short TTL plus an explicit delete |
| Profile fields | tens of seconds | 30–60 s |
| Product description | hours | hours |
| A finalised invoice | never changes again | no expiry; the key names the version |

- The number comes from the product, not from habit. "Five minutes" is almost always someone's default rather than a decision, and it is simultaneously too long for permissions and far too short for a document that cannot change
- Two rows deserve attention. Immutable data should have no TTL at all — if the value cannot change, expiry only buys misses, and the way to update it is a new key. And anything that must be revocable needs a TTL *and* a delete, because the TTL bounds the damage while the delete ends it

### The failure

- A TTL used as the only invalidation for something that must be right. Access is revoked, the database is updated immediately, and the permission cache keeps answering "allowed" until its hour is up — so the removed contractor is still authorised, and every check is working exactly as configured
- The tell is easy to apply: if someone would file an incident about the gap between the write and the next read, a TTL alone is not enough. TTL is a floor under staleness, not a mechanism for correctness, and the two get conflated because for most data the difference never shows
