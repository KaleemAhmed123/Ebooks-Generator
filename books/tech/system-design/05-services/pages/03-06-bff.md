## Backend for frontend

- A **BFF** is a backend owned by a frontend: one per user experience, web, iOS, Android, the partner API, built by the team that builds that experience, shaping the services' answers into exactly what its screens need. Sam Newman's rule: one experience, one BFF. It is where the orchestration the gateway must not do (page 5) lives

- The mobile app wants small payloads, resized images and long cache lifetimes; the web app wants wide tables in one round trip. One API serving both is a compromise that suits neither; two BFFs let each client's team change its own shape on its own schedule, which is Conway's law used on purpose (Module 1, page 6)
- The rule that keeps BFFs honest: they compose and format, never decide. Tax is calculated in one service; both BFFs call it. Newman names the risk, duplication between BFFs, and the trap in the obvious fix, that shared libraries are a prime source of coupling. Duplicated formatting is cheap; a shared "BFF core" library is a gateway in a package

### The failure

- A "general" BFF, or domain rules in a BFF. The first is a gateway with orchestration, owned by nobody who ships a screen, and every feature waits on it. The second is the same rule implemented twice, once per BFF, which agree until the day one is changed; the rule moves into the service that owns the data, and both BFFs call it
