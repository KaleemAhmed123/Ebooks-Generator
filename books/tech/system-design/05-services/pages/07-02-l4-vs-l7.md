## L4 and L7

- **L4** forwards transport packets by their five-tuple — source IP and port, destination IP and port, protocol. It never parses HTTP, never terminates TLS, and makes one routing decision per connection
- **L7** terminates TLS, reads the request, and decides per request. That is a different unit of work entirely: many requests share one connection under HTTP/2, and only an L7 balancer can spread them

| | L4 | L7 |
|---|---|---|
| Decides per | connection | request |
| Sees | IPs, ports, bytes | method, path, headers, cookies |
| TLS | passes it through | terminates it, and can re-encrypt |
| Can route `/api` and `/img` apart | no | yes |
| Cost | forwarding, near line rate | parsing and crypto, CPU-bound |
| Useful for | any TCP protocol, extreme throughput | HTTP, where routing needs the content |

- The per-connection versus per-request distinction is the one with consequences. Under HTTP/2 a client opens one connection and multiplexes hundreds of requests down it, so an L4 balancer pins all of them to whichever instance the connection landed on, and load looks even by connection count while being wildly uneven by work
- The layers compose rather than compete: L4 at the edge for throughput and DDoS absorption, L7 behind it where routing needs to read the request

### The failure

- Affinity on an L4 balancer, which can only hash the client IP. Ten thousand employees behind one corporate NAT present one source address, so the hash sends all of them to one instance — and the traffic is indistinguishable from a single very busy user, so the balancer is behaving correctly while one instance melts
- The same applies to mobile carriers, university networks and any provider doing address translation, which is most of them. Affinity that must exist belongs at L7 on a cookie the balancer sets, because that identifies a session rather than a network
