## L4 vs L7 load balancing

- Load balancers operate at different layers of the OSI network model. The two most common are Layer 4 (Transport) and Layer 7 (Application)
- An **L4 balancer** looks only at TCP/UDP packets. It sees a connection from IP `203.0.113.5` on Port `443`. It blindly forwards those raw bytes to a backend instance. It does not terminate TLS, and it does not know what an HTTP header is. It is incredibly fast and cheap
- An **L7 balancer** understands HTTP. It terminates the TLS connection, reads the URL path, the headers, and the cookies. It can route traffic based on the content (e.g., sending `/api` to one pool and `/images` to another). It is slower and uses more CPU because it has to parse the application data

| Feature | Layer 4 (TCP/UDP) | Layer 7 (HTTP) |
|---|---|---|
| **TLS Termination** | No (passes through) | Yes |
| **Routing by URL Path** | No | Yes |
| **Routing by Header/Cookie** | No | Yes |
| **Performance** | Millions of connections/sec | High, but CPU bound |

### The failure

- The failure is using L4 load balancing with "Sticky Sessions" based on the client IP address. An L4 balancer can only hash the client IP to pick a backend
- If 10,000 employees in a corporate office are all browsing your site, they might all appear to come from the exact same corporate NAT IP address. The L4 balancer will hash that single IP and send all 10,000 employees to a single backend instance, melting it down. If you need sticky sessions, you must use L7 (cookie-based)
