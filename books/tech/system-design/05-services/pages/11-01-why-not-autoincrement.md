# Module 11 - IDs, blobs, search

## Why not AUTO_INCREMENT

- A serial column makes one database the authority on identity. That is a feature at one node and three separate problems once there is more than one, or once the id is shown to anyone outside

| What breaks | Why |
|---|---|
| Sharding | two shards both hand out `1`; there is no arbiter, and merging is undefined |
| Write path | the id exists only after the insert, so nothing can be prepared before it |
| Disclosure | sequential ids publish the count and the rate of growth |
| Offline clients | a device that cannot reach the database cannot name the row it just created |

- The write-path point is the one that shapes code. With a database-assigned id you cannot build the object graph, write the audit record, or name the uploaded file until the insert returns — so a single logical action becomes a sequence of dependent round trips
- Ids generated by the caller invert this: the identity exists before the write, which makes a retry idempotent (booklet 01) because the second attempt carries the same id the first one did

### The failure

- Discovering the need to shard while every foreign key in the system is a sequence number. There is no migration that preserves them, because uniqueness was guaranteed by a property — one counter — that sharding removes by definition
- The realistic paths are all expensive: give each shard a disjoint range and accept that ranges run out, or add a new globally unique id everywhere and carry both for a year (Module 5, page 3). Choosing the id format is the cheapest decision in the project on day one and one of the most expensive in year three, which is the whole argument for spending ten minutes on it early
