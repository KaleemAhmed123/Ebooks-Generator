## Exactly-once, really

- Kafka guarantees at-least-once. If a consumer crashes after writing to the database but before committing its Kafka offset, a new consumer will re-read the same messages. You will double-count clicks
- **Deduplication:** Every click must have a unique `Click ID` generated by the frontend
- Inside the Stream Processor, you maintain a massive in-memory (or RocksDB) set of `Click IDs` seen in the last 10 minutes. If you see a duplicate, drop it
- Google's Photon system does exactly this: it joins streams and deduplicates using bounded time windows to achieve eventual exactly-once processing

### The failure

- Assuming Kafka's "Exactly-Once Semantics" (EOS) magically solves database idempotency. EOS only guarantees exactly-once *within Kafka itself* (from producer to topic to topic). Once you write to an external database, you must manually deduplicate.

:::interview
Your Stream Processor crashes. It restarts, rewinds its Kafka offset, and reprocesses the last 30 seconds of clicks. How do you prevent double-charging the advertisers?

The client must generate a unique Click ID. The Stream Processor stores these IDs in a short-lived state store (e.g., RocksDB). When it reprocesses the stream, it checks the state store and ignores duplicates.
:::\n
