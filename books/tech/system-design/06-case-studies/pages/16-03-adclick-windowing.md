## Windowed aggregation

- A Stream Processor (Flink, Spark Streaming) consumes the Kafka topic. It groups clicks into 1-minute tumbling windows
- **Event Time vs Processing Time:** You must group by the timestamp *when the user clicked* (Event Time), not when the server processed it (Processing Time)
- **Late arrivals:** A user clicks on a train, goes through a tunnel, and their phone sends the event 5 minutes later. 
- **Watermarks:** The stream processor uses a "Watermark" (e.g., 10 minutes). It keeps the 1-minute window open in memory for 10 extra minutes waiting for late clicks. Once the watermark passes, the window is closed and written to the database

### The failure

- Using Processing Time. If your Kafka consumer goes offline for 5 minutes, when it wakes up it processes all backlog events instantly. Under Processing Time, it will put 5 minutes of clicks into a single 1-minute bucket.

:::interview
A user clicks an ad at 10:01 AM. Their network drops, and the event reaches your server at 10:05 AM. Which 1-minute window should this click belong to?

The 10:01 AM window. You must aggregate using Event Time (the timestamp generated by the client device), not Processing Time (when the server saw it).
:::\n
