# Module 3 - Concurrency control

## MVCC: versions instead of blocking

- **Multi-version concurrency control (MVCC)** keeps several versions of a row and lets each transaction see the one its snapshot allows. Booklet 02 showed the storage side (an update writes a new version; vacuum removes dead ones). This page is the visibility rule
- In Postgres every version carries `xmin`, the transaction that created it, and `xmax`, the one that deleted or replaced it. A snapshot is the set of transaction ids that had committed when it was taken. A version is visible if its `xmin` is in the set and its `xmax` is not

- Readers take no locks and hold none, so a five-minute report and a thousand updates a second coexist. The price is the versions: Postgres keeps them in the table until vacuum, InnoDB in the undo log, and either grows for as long as the oldest snapshot lives (Module 1, page 7)

### The failure

- Treating MVCC as protection for writes. It protects reads: your snapshot is consistent. It does nothing for a value you read, compute on, and write back; a newer version may already exist and your write lands on top of it (Module 2, page 6). Isolation of reads is not isolation of decisions
