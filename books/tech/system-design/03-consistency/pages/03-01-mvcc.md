## MVCC: Versions instead of blocking

- The oldest way to implement transaction isolation is locking: if you are reading a row, no one else can write to it until you finish. This is safe, but it makes the database unacceptably slow for read-heavy web applications
- Almost all modern databases solve this using **Multi-Version Concurrency Control (MVCC)**
- Instead of updating a row in place, MVCC writes a completely new version of the row, tagged with the ID of the transaction that created it (`xmin` in Postgres). Readers then look at the history of the row and pick the version that was visible exactly when their snapshot started

- **The garbage problem**: If every update creates a new row, the disk will fill up forever. The database must constantly run a background process to find and delete rows whose `xmax` (deleted-by ID) is older than any currently running transaction. Postgres calls this **Vacuum**; InnoDB handles it via the **Undo Log**

### The failure

- An open transaction blocking the vacuum. If a single developer opens a `psql` console, runs `BEGIN`, and walks away for the weekend, they freeze the MVCC horizon. The database is forced to keep every single old version of every single row updated over the weekend, just in case that developer runs a `SELECT`. The disk bloats, storage fills up, and the database crashes
